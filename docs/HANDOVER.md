# Hand-over notes

For whoever looks after this fleet system next. It serves one or more agencies; GEMA is the first. Anything below that says "the site" means all agencies together, and "the agency" means one organisation's own records.

## Who can do what

- **Super user.** One or more email addresses listed in the Cloudflare secret `SUPERUSER_EMAILS` (set separately on the production and staging Workers; comma separated, case does not matter), **on an account in the home agency**. The home agency is `SUPERUSER_AGENCY` in the same file (default `GEMA`). An account with a super user's email in any other agency is an ordinary account, and nobody can create, edit or invite an account with such an email outside the home agency (the server answers 400 `reserved_email`). It is kept as a secret, not in `wrangler.jsonc`, so the address isn't published with the code. Set or change it with `npx wrangler secret put SUPERUSER_EMAILS` (add `--env staging` for staging), or in the Cloudflare dashboard: Workers & Pages > the Worker > Settings > Variables and Secrets > Add, type **Secret**. A change takes effect straight away, without a deploy. For local development, put `SUPERUSER_EMAILS=you@example.org` in `.dev.vars` (never committed). A super user has every permission whatever their role, and nobody else can edit, deactivate, change the role or permissions of, set the password of or send reset links to a super user's account. If the variable is empty, nobody is a super user. The account itself is an ordinary user created as usual (for example with `npm run create-admin`); it becomes a super user because its email matches. To hand over: set the secret to both addresses, then later to the new one only.
- **Features (super user only).** Setup > **Features** shows a **Photo and PDF uploads** switch. It is **off by default** because file storage is limited. While off, every upload button (Report a problem, problem and work order Attachments) stays on screen but disabled with the note "Photo and PDF uploads are turned off for now.", and the server refuses uploads for everyone, including the super user, with `403 uploads_disabled`. Existing files can still be opened, and fleet managers and system administrators can still remove them. To turn uploads on, open Setup as the super user, tick the switch and press **Save features** (turn it off the same way). The switch is **per agency**: it lives in that agency's settings record under `features.uploads`, so to change it for another agency use **Open** on the Agencies screen first, change it, then go back. A new agency starts with uploads off; a missing value means off, and the ordinary **Save settings** can never change it. When it is on, only people with the **Upload photos and PDFs** permission can upload.
- **The three admin levels.**

  | | Fleet manager | System administrator | Super user |
  | --- | --- | --- | --- |
  | Who | A role (by default: whole fleet, setup, approvals, users) | A role (by default: everything a fleet manager has) | An email in `SUPERUSER_EMAILS`, whatever their role |
  | Add people, set roles, passwords, deactivate | Base supervisor and below | Fleet manager and below | Anyone except themselves |
  | Per-person permissions (Users > Permissions) | **No** (button hidden, API answers 403) | Fleet manager and below | Anyone except themselves |
  | Role permissions (Roles & permissions) | **No** (link hidden, API answers 403) | Fleet manager, base supervisor, mechanic, crew, dispatcher, viewer; the system administrator column is view only | Every role |
  | Grant Manage people or Change setup (to a role or a person) | No | No | Yes |
  | Backups panel, list, download, run | No | **No** | Yes |
  | Features (uploads switch) | No | No | Yes |
  | Agencies screen (add, rename, deactivate, open) | No (link hidden, API answers 403) | **No** | Yes |

  Everything else in this table applies **inside one agency**: a fleet manager or system administrator manages only their own agency's people, roles and settings. You can only switch ON what you have yourself. **Backups** belongs to the super user alone: no role default includes it, it is not listed in either permission editor, and the server rejects any attempt to grant it by role or person (400); a stray stored value is ignored. The nightly backup runs on a schedule and is unaffected.
- **Roles & permissions.** Admin > **Roles & permissions** (`#roles`, super user and system administrators only) is a matrix: one row per permission (grouped: Units, Problems, Work orders, Parts and mechanics, Admin), one column per role. Columns you cannot edit are greyed and read-only. **Changed** marks a cell that differs from the built-in default (`PERM` in `src/shared/perm.ts`). Ticking boxes changes nothing until you press the one **Save changes** button at the top right of the page: unsaved boxes are highlighted, the header counts them, **Discard changes** puts them back, and the browser warns before you close or reload the tab with unsaved edits. **Save changes** saves every changed role together, all or nothing, after a confirmation that names the roles and how many people they affect. **Reset to default** (under each column) only fills in that role's built-in defaults; it too is kept by **Save changes**. On a phone a role picker shows one column at a time. Changes are stored in the settings record under `rolePerms` ({ role: { key: true/false } }, only differences from the defaults), written only by `PUT /api/roles/permissions` (several roles at once; the page uses this), `PUT /api/roles/:role/permissions` and `POST /api/roles/:role/reset` (audit-logged as `role.permissions` / `role.reset`, one row per changed role, with before and after). The ordinary **Save settings** can never change `rolePerms`, and neither can a crafted request. A change reaches everyone in the role within about 20 seconds with no new login. The order of precedence is: super user (always yes) > the person's own change > the role's change > the built-in default.
- **Per-person permissions.** Users screen > **Permissions** (super user and system administrators only) opens one person's switches (grouped like the matrix). Each switch shows what the person can do now and where that comes from: **Role default**, **Role change** (set on Roles & permissions) or **Personal change** (marked **Changed**), with **Reset to role default** per switch and **Reset all to role default**. Only the differences from the person's role (default plus role change) are stored (`users.perm_overrides`, migration 0003). Changes reach that person's screen within about 20 seconds with no new login. Changing someone's role keeps their personal changes; they are then compared with the new role. Scoping still applies on top: a base supervisor or crew member's rights apply to the units at their bases (crew and others with no base set see every unit), and a mechanic only works on work orders assigned to them. **View reports** only hides the Reports screen; it does not hide data the person can already read.
- **Who can change whom.** The super user: anyone but themselves. A system administrator: fleet managers and every role below. A fleet manager: base supervisors and every role below (accounts and roles only, not permissions). Nobody changes their own role or permissions. The same limits apply when adding people and choosing their role (only the super user can create a system administrator).
- **Users screen** (fleet manager and system administrator): add a person, change role or bases, set a password, deactivate; **Permissions** for system administrators and the super user. Only the super user can create or change system administrator accounts.
- **Adding a person.** Choose **Set a password now** (type one or press Generate, then hand it to them; they are not forced to change it, and the screen does not show it again) or, when email is set up, **Email an invite link** (they choose their own password; the list shows "Invited — not yet set up" until they do, with a **Resend invite** button). You can set a new password for anyone later with **Set password** (it logs them out everywhere). Everyone can change their own password with the **Password** button.
- **Email is optional.** Without it the Users screen says "Email isn't set up, so you choose people's passwords here." With it, people get **Forgot password?** on the login page and you get **Send reset link**. Setup, limits and what to do if it stops working: [EMAIL.md](EMAIL.md).
- **Locked out?** After 10 wrong passwords an account is locked for 15 minutes. A forgotten password is fixed with **Forgot password?** (if email is set up) or by an administrator with **Set password**.
- **Nobody can log in as administrator?** Create one from a computer that has this repository and is logged into Cloudflare: `npm run create-admin -- --email ... --name ... [--agency CODE] --remote` (the agency defaults to `GEMA` and must already exist) (add `--invite` for a set-password link, or `--password-prompt` to type a password at a hidden prompt).

## Agencies

An **agency** is one organisation using the site. Each has its own bases, vehicles, PM programs, parts, mechanics, work orders (numbered from WO-0001 in each agency), problems, people, role changes, settings, files and Activity history. Existing data from before agencies existed belongs to the first agency, `GEMA` (migration `0005_agencies.sql`).

**Signing in.** The login page asks for an **Agency ID**, then email and password. The Agency ID is not case sensitive, extra spaces are ignored, and the browser remembers the last one used. A wrong Agency ID, an unknown one, a deactivated agency, a wrong email and a wrong password all give the same message ("Wrong Agency ID, email or password."), so the page does not reveal which agencies exist. The lockout (10 wrong passwords, 15 minutes) counts per agency and email. The same email address can be an account in two agencies; they are separate accounts with separate passwords. Invite and reset emails name the agency and its Agency ID, and **Forgot password?** asks for the Agency ID too.

**How to add an agency** (super user only):

1. Open **Admin > Agencies** (`#agencies`) and press **Add agency**.
2. Enter the **Agency ID** (2 to 20 characters: letters, numbers, hyphens; saved in capitals; cannot be changed later), the **name** (shown in the sidebar and page title), and the **first system administrator**: name, email and a password (type one, or **Generate**; same rules as the Users screen). The agency, its default settings, that administrator and the audit rows are all created in one step.
3. Give the administrator three things: the Agency ID, their email and the password. (They are not forced to change it, the same as an account added on the Users screen.)

**What the agency administrator does next.** Log in, then in **Setup** add the bases, the PM programs and the settings (approval threshold, PM "due soon" window), then add vehicles, then add people on **Users** (fleet managers, supervisors, mechanics, crew, dispatchers). A new agency starts completely empty (no sample data), and the screens say what to do first. If email is set up (see [EMAIL.md](EMAIL.md)) they can invite people by email.

**Other things you can do on the Agencies screen.** The list shows each agency's ID, name, state, active users, vehicles (not counting decommissioned ones) and created date. **Rename** changes the name only. **Deactivate** stops everyone in that agency from logging in and ends all their sessions at once; nothing is deleted, and **Reactivate** undoes it. The home agency cannot be deactivated. **Open** switches *your own session* into that agency so you can help its people: a banner says "Viewing <name> (<CODE>) as the super user" with a **Back to <home agency>** button, you see and change that agency's data, and every change is recorded in that agency's Activity history under your email. Other people's sessions are not affected, and a new login starts in your home agency again.

**How separation is enforced** (all on the server; the browser is not trusted):

- Every agency-owned table has an `agency_id` column. Every SELECT filters on it, every INSERT sets it and every UPDATE and DELETE adds `AND agency_id = ?`. An id from another agency therefore behaves exactly like an id that does not exist (404 or 400).
- `requireAuth` in `src/worker/auth.ts` decides which agency a request belongs to, from the session and the user's row, never from anything the browser sends. Only the super user's session can act in another agency, and only an active one. Everything after it reads `actor.agencyId`.
- Writes go through `Tx` (`src/worker/db.ts`), which carries the agency, stamps it on audit and tombstone rows, and refuses to exist without one. `agencyRow` and `inAgency` (same file) check that an id belongs to the agency before anything uses it.
- Reads for the screens go through `loadDocs` / `loadDoc` (`src/worker/docs.ts`) and `syncSince` (`src/worker/sync.ts`), which always add the agency filter. Activity history and its CSV filter in `fetchRows` (`src/worker/activity.ts`). Files are stored under `attachments/<AGENCY>/<id>` for new uploads, and downloads check the attachment row's agency, not the key.
- The test file `test/api/agencies.test.ts` builds two agencies and checks both directions: lists, sync, history, CSV, settings, roles, and every endpoint that takes an id. When you add an endpoint that takes an id, add it to the list in that file. The rule for new code is in [SECURITY.md](SECURITY.md), *Tenant isolation*.
- Not per agency, on purpose: the change counter (`counter`), the forgot-password throttle (`auth_throttle`) and the backup records. The nightly backup is **one file for the whole database** (all agencies) and only the super user can see or download it; see [RESTORE.md](RESTORE.md).

### Activity history (who changed what, and when)

Every change a person makes, and every sign-in, is recorded in the `audit_log` table (who, when, what, before and after). The **super user and system administrators** read it in the app at **Admin > Activity history** (`#activity`); nobody else sees the link, and the API answers 403 to everyone else (the rule is `isSuper || role === 'system_admin'`, in `src/worker/index.ts`).

- **What you see.** Newest first, grouped by day (Guyana time), 50 at a time with **Load more**. Each row: time, person (their *current* name and role; deactivated people are marked), and a plain-English sentence ("Moved GEMA-03 from HQ to Linden", "Changed Jane Doe's role from Crew to Base supervisor", "Failed sign-in for jdoe@example.org"). Unit, work order and person names are links. **What changed** on a row shows the fields that differ, before and after (dates as DD/MM/YYYY, G$ amounts, base names, role labels, yes/no).
- **Filters.** Search (action, item id, person name or email, unit name, work order number), Person, Type, From/To dates (Guyana calendar days). Types: Vehicles, Problems, Work orders, Preventive maintenance, Parts & mechanics, People & permissions, Settings & features, Sign-ins (includes password changes and resets), Backups. **Export CSV** downloads the current filtered view (newest 5,000 rows; the screen says when the limit was hit; narrow the dates for the rest).
- **Shortcuts.** Users > **View activity** opens it for one person; a unit's History tab has **View activity for this unit**.
- **What is recorded.** Every write in the app (units, readings, problems, work orders and their lines, parts, mechanics, bases, PM programs, settings, features, roles and permissions, users, files, backups, sample-data removal) and sign-ins: `auth.login`, `auth.logout`, `auth.login_failed` (the email address that was tried, and the account if it exists; **never the password**; text that is not an email address is not kept at all), `auth.locked` (written once, by the 10th wrong password), `auth.change_password`, `auth.set_password`, `auth.forgot_password`. Attempts made while an account is already locked are not logged (they would only fill the table).
- **Where the code is.** One table maps actions to Types and one function describes each action in `src/shared/activity.ts` (unit tested); the query side is `src/worker/activity.ts`; the screen is `src/client/activity-ui.ts`. **Adding a new kind of audited change:** call `tx.audit('thing.verb', 'thing', id, before, after)`, then add a prefix to `CATEGORY_RULES` and a sentence to `DESCRIBE` in `src/shared/activity.ts`. Until you do, the row shows as "Other" with a generic sentence ("Updated ...") and is still found by search. The unit test lists every action the Worker writes and fails if one has no Type.
- **Size.** Rows are small (one per write); a year of normal use is tens of thousands of rows. Migration `0004_activity_indexes.sql` adds the indexes the screen needs (person, item, date). There is no automatic clean-up; the nightly backup includes the table.

## Bus checks (start-of-shift ambulance inspection)

**What it is.** A crew member opens **Operations > Bus check** on their phone, picks the unit, and does the full inspection: crew, mileage and engine hours, every item on the list for that kind of unit, any extra problems, and a confirmation tick. Managers read the results at **Admin > Bus checks**. The owner's decisions: it is always the full check (no quick version); different units can have different lists; a crew can send a check with shortages; **equipment shortages are kept apart from vehicle problems** (below), and only a problem the crew types in themselves goes to maintenance; fleet managers, system administrators and the super user can change the requirements.

**Who can do what** (four switches in Roles & permissions, so they can also be changed per role or per person; the server checks every one, the screen only hides what a person cannot use):

| Switch | Default roles | Notes |
| --- | --- | --- |
| Do bus checks | Crew, base supervisor, fleet manager, system administrator | Only on units the person may act on: crew at their bases (all units if they have no bases set), base supervisors at their bases |
| View bus check reports | Base supervisor (their own bases only), fleet manager, system administrator | Today, Equipment, Shortage report, History, one check, CSV exports, the unit's Bus checks tab |
| Mark equipment restocked | Base supervisor (only units at their own bases), fleet manager, system administrator | The Mark restocked buttons. This switch alone (without the reports switch) is also enough to see the Equipment tab and the unit's shortages |
| Edit bus check requirements | Fleet manager, system administrator | The Requirements tab. The super user can do everything |

**Requirement lists.** A list has a name, the unit types it covers (the `Type` of the unit, for example "Type II ambulance"), an active switch, and sections of items. A unit uses the active list that names its type; if none does, the active list with **no** unit types (the default). The server refuses to save two active lists that name the same type, or two defaults, so only one list ever applies. An item is one of five kinds: *count* (a minimum quantity: the crew answer OK or Short, and Short needs a whole number below the minimum), *check* (Pass or Fail), *number* (a reading with a minimum, for example oxygen pressure), *date* (a date that must not have passed, for example a cylinder test) and *optional* (present or not there, never a shortage). Nothing is added by the migration: an agency with no list sees **Start from the standard list** (based on the equipment sections of the NYS DOH-3780 ambulance check sheet, 79 items in 8 sections, which is then editable like any other). Lists can be duplicated (the copy is inactive until it is given unit types), renamed, re-typed, edited (add, change, remove, move up or down), and made inactive. Every change is in Activity history.

**A sent check never changes.** Each check keeps its own copy of the list it was done against and of every answer, so editing a list later does not rewrite history. There is no edit or delete for a check, in the screen or the API.

**What sending does.** In one database write, the server saves the check, the meter reading (source `bus_check`, with the same limits and "looks wrong" flagging as Log engine hours), the vehicle problems the crew reported, and one **equipment shortage** for each shortage. Titles read like `Bus check: Sterile gauze pads 4x4" short (2 of 6)`, `Bus check: Seatbelts failed`, `Bus check: Oxygen cylinder 1 pressure 800 psi (minimum 1000)`, `Bus check: Portable oxygen cylinder 1 hydrostatic test expired 01/02/2025`. If the unit already has an **open** shortage for the same item, the new finding is added to it (a "Found again" line is appended to its description) instead of creating another. Once that shortage is **restocked**, the next check that finds the item short creates a **new** shortage (the closed one is not reopened). The crew's confirm and done screens say so: shortages are "recorded for restocking", problems they reported are "sent to maintenance as vehicle problems".

**Equipment shortages are not vehicle problems (owner's decision).** A shortage is still a row in the `issues` table (`source = 'bus_check'`, `source_ref` = the list item id, `bus_check_id` = the check that found it; that is what de-duplication, the links and the history use), but it is filtered out of everything that is about the vehicle: the Problems page and its counts and filters, the unit page's Issues tab and counts, the status board and dispatch badges, the Critical issues count, the work order "create from selected problems" flow, the Reports screen, and anything that decides availability. It works like this: the sync never sends `source = 'bus_check'` rows (`syncWhere` on the `issues` spec in `src/worker/docs.ts`, used by `src/worker/sync.ts`; the browser also drops any that slip through in `applySync`); `POST /api/issues/:id/dismiss`, `POST /api/work-orders` with such an id, and uploading a file to one answer 404; completing or reopening a work order never touches one. A shortage never changes a unit's status (the old rule that it is never Critical stays; the severity stored is only used for the title). A problem the crew types in (`source = 'bus_check_report'`) stays an ordinary vehicle problem with the small **Bus check** label, and a Critical one takes the unit out of service as before. **If you add a new place that reads `issues`, exclude `source = 'bus_check'` there** (or read it from the sync, which already does).

**Restocking.** **Mark restocked** (one shortage, or **Mark all restocked** for a unit) opens a small confirm with an optional note (200 characters), then `POST /api/bus-checks/equipment/restock { ids, note }` sets the shortage's status to `restocked` (added to `ISSUE_ST` as "Restocked"; the status column is free text, so no migration of old rows), stores who and when (`issues.restocked_by`, `issues.restocked_at`, migration `0007_bus_check_restock.sql`), appends `Restocked by <name> on <date>. Note: ...` to its description, and writes one `issue.restock` audit row each ("Marked 'Gauze short (2 of 6)' restocked on GEMA-03 (note)" in Activity history), all in one batch. If any id is not a shortage of this agency, or is on a unit outside the person's bases, the whole request answers 404 and nothing changes; an already restocked one answers 409. `restocked` leaves the partial unique index on open shortages, which is what lets a later shortage start a new row.

**Shifts.** Setup > Settings has **Bus check shift start times** (default `07:00, 19:00`, Guyana time, 1 to 6 times at least 2 hours apart). A check counts for the shift whose window contains the moment it was sent. A shift's window starts **one hour before** the shift starts and ends one hour before the next shift starts, so a check done at 06:20 counts for the 07:00 shift and one done at 18:05 counts for the 19:00 shift; a check sent after midnight belongs to the evening shift that started the day before. The **Today** tab shows, for each unit that is expected to be checked and each shift of the chosen day: **Checked** (who, when, how many shortages, a link), **Missed** (the window has closed with no check), **Due** (the window is open and the shift has started), **Not started** (shift not started yet) or **Not expected** (the unit was out of service when the shift started, or was not in the fleet yet). A unit that is out of service but was checked anyway shows Checked. If a unit has two checks in the same window, the first is shown and the cell says how many there were.

**Reports** (Admin > Bus checks, tabs in this order): *Today* (above, with a date picker and counts of checks done, missed and with shortages), *Equipment* (the open shortages grouped by base and then unit, each with the item, what was found the last time, first found, how many checks found it, and the last check; filters for station and unit; **Mark restocked** / **Mark all restocked** per unit; a collapsible **Restocked recently** (last 30 days, with who, when and the note); CSV of the open shortages), *Shortage report* (formerly "Shortages": date range, default the last 30 days; the items most often short, with the number of units, and the units with most shortages; CSV), *History* (newest first, 50 at a time; filters for unit, station, person, dates and only checks with shortages; open one to see the whole check read-only; CSV), *Requirements* (only with the edit switch). A unit's own page has a **Bus checks** tab that also lists the unit's open equipment shortages (with Mark restocked when allowed). The crew's Bus check screen shows, once a unit is chosen, a **Known shortages on this unit** panel (`GET /api/bus-checks/equipment/known?vehicleId=`, needs only the right to do bus checks on that unit). CSV exports stop at the newest 5,000 rows and say so.

**Equipment endpoints** (all start with the caller's agency; another agency's id is "not found"):

| Method and path | Needs | Scope |
| --- | --- | --- |
| `GET /api/bus-checks/equipment?baseId&vehicleId&recent=1` | reports **or** restock | supervisors: units at their bases; filters naming a unit or base outside the agency or the bases: 404 |
| `GET /api/bus-checks/equipment/export?baseId&vehicleId` | reports **or** restock | same; CSV of the open shortages |
| `GET /api/bus-checks/equipment/known?vehicleId=` | do bus checks | units the person may check |
| `POST /api/bus-checks/equipment/restock` `{ ids, note? }` | restock | units at the supervisor's bases (404 otherwise) |

**Agency and base rules.** Both new tables carry `agency_id`; every query starts with the caller's agency from the session, and every id that arrives from the browser (unit, base, list, person, check) is looked up inside that agency first, so another agency's id behaves like one that does not exist (404, or 400 for an id inside a form). A base supervisor's reports cover the units **currently at** their bases (a unit moved away disappears from their Today and Shortages); their History base filter is the station the crew entered. Asking for a unit, station or person outside the agency or the person's bases is "not found".

**Things to know.**
- Each check stores its list and answers (roughly 10 KB), so about 20 KB per unit a day with two shifts. A fleet of 20 units makes about 150 MB a year in the database and the nightly backup. If that ever matters, store only the answers and a version of the list instead.
- The crew's unsent check is kept in the browser (per person and unit, for 24 hours) so a lost signal does not lose the work. It is deleted when the check is sent.
- Sending twice (a double tap, a retry after a lost connection) saves one check: the browser sends a reference and the server returns the first result. Two crews sending a check for the same unit at the same moment cannot create two shortages for the same open item (a database index guards it and the second attempt joins the first).
- A "looks wrong" reading (lower than the unit's current reading, or more than 24 hours a day since the last one) is saved flagged and does not change the unit's hours until a supervisor accepts it, exactly as for Log engine hours. The check itself is still saved.
- Where the code is: shared rules (item kinds, shortages, list choice, shifts) `src/shared/buscheck.ts` and the starter list `src/shared/busCheckStarter.ts`; the server `src/worker/buscheck.ts`; the screens `src/client/buscheck-ui.ts` (do a check), `buschecks-ui.ts` (reports) and `busreq-ui.ts` (requirements); table definitions `migrations/0006_bus_checks.sql` and `0007_bus_check_restock.sql`; tests `test/api/buscheck.test.ts`, `test/unit/buscheck.test.ts` and the bus check part of `scripts/e2e.mjs`.

## Demo

**Try the demo** on the login page opens the app on the GEMA sample fleet (`src/shared/sample.ts`, the same data as `npm run seed:demo`) with no account.

- **How it works.** The real API (`src/worker`) runs inside the visitor's browser tab against an in-memory SQLite database ([sql.js](https://github.com/sql-js/sql.js), SQLite compiled to WebAssembly) built from `migrations/` and the sample data. While the demo is open, every request the screens make goes to that copy instead of to the server (`setTransport` in `src/client/api.ts`). So every rule and permission behaves exactly as it does for real, the demo never reads or changes real data, and closing or reloading the page throws everything away. There is nothing to reset and nothing to clean up.
- **People.** One demo person per role, picked from the menu at the top right (`DEMO_PEOPLE` in `src/demo/server.ts`): Andrea Singh (system administrator), Marcus Thomas (fleet manager, the starting person), Kavita Ramdass (base supervisor for HQ and Diamond), Devon Charles (mechanic at Linden Motor Clinic), Shanice Williams (crew at HQ), Ravi Persaud (dispatcher) and Joanne Baptiste (viewer). Switching keeps the same page when the new person may see it. There is no super user in the demo.
- **Left out on purpose.** Photo and PDF uploads stay off and the switch cannot be reached (the upload buttons say "not available in the demo"); backups, agencies, removing the sample data, signing in with a password, changing passwords and email links are refused with a short message (`BLOCKED` in `src/demo/server.ts`). Log out becomes **Exit demo**.
- **Cost.** The demo engine (about 410 KB compressed) is a separate download that only happens when someone clicks **Try the demo**; people who log in normally never load it. The demo makes no requests to the Worker, so it does not use the free plan's daily allowance.
- **Security header.** Running WebAssembly needs `'wasm-unsafe-eval'` in the page's `script-src` (`public/_headers`). That allows compiling WebAssembly only; JavaScript `eval` and inline scripts are still blocked.
- **When the database changes.** New migrations are picked up automatically. If a migration needs data the sample does not have, update `src/shared/sample.ts` (or `src/demo/server.ts`). `test/unit/demo.test.ts` starts the demo, signs in as every person and checks the refusals.

## Choices worth knowing

- **Sample data** is marked in the database (`sample = 1`) so it can be removed in one step without touching real records.
- **Settings** are one record per agency (its id is the agency code; the first agency's record was `main` before migration 0005). They hold the approval threshold (work orders over this need a fleet manager), the PM "due soon" window and the comeback window.
- **Password hashing** is set to 20,000 rounds to fit the free plan. See [SECURITY.md](SECURITY.md). If the account is upgraded to a paid plan, raise `PBKDF2_ITERATIONS` in `wrangler.jsonc` to 100000 or more; existing passwords are upgraded automatically at each person's next login.
- **Restoring** is in [RESTORE.md](RESTORE.md).
